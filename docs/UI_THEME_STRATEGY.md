# Beecord UI 与主题架构演进储备

> 状态：**v0.1 方法论记录（2026-11-22）**。本文是后续设计评审与实施规划的输入，
> **未评审、未排期、未实施**，不改变任何现行页面、组件、令牌或交互约定。
>
> 现行规范仍以 [`DESIGN_SYSTEM.md`](DESIGN_SYSTEM.md)、[`ux-design.md`](ux-design.md)、
> [`ux-device.md`](ux-device.md) 为准；测试要求仍以 [`TESTING.md`](TESTING.md) 为准。
> 后续若要实施本文任一内容，须先形成独立方案；涉及视觉或布局变化时，仍须遵守原型先行和截图验收。

## 1. 记录目的

本文沉淀其他成熟 macOS 项目的 UI 实现方法论，并结合 Beecord Studio 与手表固件现状，
形成一套适用于本项目的演进思路。重点不是复制某个 `DSN` 命名空间、类结构或色值，而是回答：

1. 如何避免各页面分别解释颜色、字体、间距和控件状态，长期保持视觉一致。
2. 如何让一种设计风格作用于整个应用，而不是逐页改色、逐控件修补。
3. 如何让 Mac 与手表共享相同的产品语义和品牌气质，同时保留各自平台习惯与硬件约束。
4. 如何用测试和视觉证据证明主题应用正确，而不是只证明“代码集中了常量”。
5. 如何渐进演进，避免一次性重写现有 SwiftUI、LVGL 页面和业务逻辑。

### 1.1 核心结论

**视觉统一的关键不是统一色值，而是统一 UI 决策发生的层级。**

页面应描述业务内容、业务状态和组件组合；主题应描述这些语义在某种设计风格下如何表现；
平台组件应负责把这种表现落实为颜色、字体、形状、交互和辅助功能。页面不应知道当前主题名，
也不应通过主题条件分支决定局部样式。

### 1.2 非目标

- 不追求 Mac 与手表像素级一致，不共享 UI 控件代码。
- 不复制 AppKit 自绘控件体系，不把 SwiftUI 原生控件全部重写为自定义控件。
- 不为了“支持主题”立即建设通用主题包格式、在线主题下载或用户主题编辑器。
- 不建立全页面逐像素黄金图比对作为主要 CI 门禁。
- 不把主题切换做成业务重置：不得中断录音、播放、下载、连接、导航或未保存编辑。
- 不在本文拍板任何新配色、字体、圆角、动画或用户可见主题入口。

## 2. 可借鉴的 UI 实现思想

### 2.1 语义、主题表达、平台映射分离

一套可主题的 UI 需要在概念上区分三类决策：

| 决策层 | 回答的问题 | 例子 | 不应承担 |
|---|---|---|---|
| 产品语义 | 这个信息或操作是什么意思 | 主操作、次操作、录音中、同步中、危险、成功、弱说明、内容面、选中态 | 具体 HEX、某个平台的控件类名 |
| 主题表达 | 这种设计风格如何表达该语义 | 品牌色、文字层级、卡片层次、圆角、边线、密度、图标风格、动画节奏 | 业务流程、页面数据、权限判断 |
| 平台映射 | 当前平台如何正确实现 | SwiftUI button style、系统字体样式、LVGL style、字库、触控区域、键盘焦点 | 另造产品语义、跨平台强求同值 |

这层分离带来的收益是：

- 更换主题时，业务语义不变，只替换表达和必要的平台映射。
- 新增页面时，从既有语义和组件中组合，不需要重新发明视觉语言。
- 修复平台问题时，不必改变产品语义，也不必把平台特判散到所有页面。
- Mac 和手表可以共享“录音中”“危险操作”“次说明”等含义，而采用不同视觉载体。

### 2.2 主题不是调色板，而是一整套设计语言

仅以 `primary/secondary/background` 一组颜色描述主题，通常只能得到“换色”，得不到完整风格。
后续评审一种设计风格时，至少要检查以下维度：

| 维度 | 需要统一的决策 | 常见失控方式 |
|---|---|---|
| 色彩语义 | 品牌、操作、状态、文字、表面、描边、遮罩、内容图形 | 页面直接选色；状态色与品牌色混用 |
| 字体角色 | 页面标题、分组标题、正文、辅助、弱信息、数字、等宽内容 | 页面直接写字号；数字宽度跳动 |
| 空间与密度 | 间距节奏、控件高度、内边距、列表密度、页面留白 | 每页一套间距；为了塞内容随意压缩 |
| 形状 | 卡片、按钮、行、浮层、胶囊的圆角语言 | 同族组件圆角不一致 |
| 边界与层次 | 分隔线、卡片底、阴影、材质、浮层与内容区的层级 | 所有卡片都加边框和阴影；层级靠堆效果 |
| 图标 | 图标族、线宽、填充规则、尺寸、着色和装饰性处理 | 同页混用不同风格；用语义不清的符号代替 |
| 动效 | 时长、缓动、反馈类型、循环动效、减少动效回退 | 每页自定义动画；装饰动效干扰业务状态 |
| 控件状态 | 默认、hover、pressed、selected、disabled、focus、loading、error | 只设计默认态；每页自行解释禁用和选中 |
| 内容图形 | 波形、进度、标记、录音电平、状态点、空态插图 | 内容图形绕过语义色，换主题后残留旧色 |

因此，“应用一种主题”的完整含义应是：**保持产品语义和交互不变，系统性地替换上述表达规则，
并验证所有组件状态和关键页面状态。**

### 2.3 组件是主题的作用边界，页面不是

主题最适合作用于共享组件和语义样式，而不是页面文件。页面只应保留：

- 业务数据与状态。
- 信息层级和组件组合。
- 真正的页面级布局关系。
- 经过规范登记的少数布局例外。

按钮、徽章、卡片、表单字段、列表行、Toast、空态、浮层等组件，应集中持有其状态表现。
否则即使所有色值都来自令牌，不同页面仍会把同一个语义组合成不同视觉效果。

需要特别区分：

- **令牌集中**解决“数值写在哪里”。
- **组件集中**解决“这些数值如何组合成一致行为”。

只有前者而没有后者，仍会出现同令牌、不同观感。

### 2.4 状态矩阵比默认态截图更重要

成熟组件规范不能只描述静态外观。每类组件应明确支持哪些状态、哪些状态可叠加，以及优先级。
例如：

- 选中与 hover 同时存在时谁优先。
- 禁用是否还响应 hover、焦点和点击。
- 加载中原有结果是否保留，操作是否禁用。
- 错误与聚焦同时存在时如何表达。
- 未读、未恢复、已恢复是否只依赖颜色区分。
- 录音中与暂停、无卡、写错误之间如何投影到 UI。

状态矩阵既是设计规范，也是测试目录。它能防止“默认页很美，异常态和禁用态各自长一套”。

### 2.5 交互行为与视觉表达分开治理

原生控件的价值不只是外观，还包括键盘、焦点、朗读、命中区域、菜单、禁用和系统状态。
应用设计风格时，应优先改变共享样式，不应为了匹配原型而丢掉这些行为。

- Mac 原生按钮、开关、菜单、分段控件继续由系统提供基本交互。
- 自绘侧栏项、波形、特殊确认层才补自定义视觉和必要行为。
- 手表可以自定义 LVGL 组件外观，但触控目标、按压反馈、事件穿透和高优先级浮层规则不能随主题改变。

**风格可以替换，可操作性不能降级。**

### 2.6 动态解析与业务状态保持

如果未来支持运行时主题切换，应满足：

- 新主题对所有可见组件生效，不残留旧色、旧图标或旧字体。
- 手工写入绘图层的颜色有统一刷新路径，不能依赖偶然重绘。
- 切换主题不重建业务会话，不清空页面数据，不改变导航和滚动位置。
- 系统外观、增强对比度、降低透明度、减少动态效果与主题表达有明确优先级。
- 主题资源加载失败时有可预测的完整回退，不能出现半个新主题、半个旧主题。

首版抽象不应为了未来切换而缓存大量“当前颜色”。先保证解析路径唯一，再决定是否有运行时入口。

### 2.7 跨平台统一的是语义和气质，不是数值表

Mac 与手表应共享：

- 品牌定位。
- 信息层级。
- 操作层级。
- 录音、同步、成功、警告、危险等状态含义。
- 字体、图标、动效的整体性格。
- 空态、错误态、禁用态的表达原则。

不应强求共享：

- 相同字号、控件高度、页面 padding。
- 相同圆角和阴影。
- 相同 hover、focus、透明度行为。
- 相同背景亮度和大面积色彩策略。
- 相同动效数量和渲染成本。

Mac 是键盘、指针、窗口、系统字体和动态外观环境；手表是小屏、触控、固定视口、
字库资源、AMOLED 功耗和实时任务环境。平台差异应通过能力档案和映射规则显式表达。

### 2.8 视觉质量必须形成证据闭环

“使用了设计系统”不等于视觉正确。完整证据包括：

1. 语义和主题值测试：证明规则完整、值符合评审、派生关系未被误改。
2. 组件行为测试：证明状态、键盘、触控、禁用、焦点和朗读没有回归。
3. 少量布局不变量：证明关键内容没有越界、重叠或被裁掉。
4. 同场景截图与读图：证明实际视觉层级和绘制效果符合原型。
5. 真实环境验收：证明系统设置、窗口变化、硬件资源与长时间运行下仍正确。

截图不能替代行为断言，行为断言也不能替代读图。

## 3. 主题化边界

### 3.1 应保持稳定的产品不变量

| 类别 | Beecord 中应保持的内容 |
|---|---|
| 信息与流程 | 页面职责、导航、下载与播放流程、录音操作流程 |
| 状态含义 | 录音中、暂停、同步、校验、失败、未连接、未知数据等语义 |
| 安全 | 危险操作确认、格式化确认、按住停止、错误如实反馈 |
| 可访问性 | Mac AX id、标签、值、键盘路径；手表最小触控目标 |
| 数据诚实性 | 不用占位数据冒充真实状态；未知和拒判仍有明确表达 |
| 布局底线 | Mac 最小窗口和关键操作可达；手表安全区、圆角裁切避让 |
| 领域色义 | 危险、警告、成功、录音等语义不能被品牌换色反转 |

### 3.2 可以主题化的表达

- 品牌强调色及其在允许场景中的使用方式。
- 中性表面层级、描边强弱、透明或实色策略。
- 字体族和字重倾向，但必须受平台字库与可读性约束。
- 控件和卡片的圆角语言。
- 间距密度预设，但不能突破最小命中区域和内容地板。
- 图标族、线宽、填充和着色规则。
- 阴影、材质、边框之间的层次选择。
- 动效节奏，但必须有减少动效与低性能回退。
- 波形、电平、进度等内容图形的视觉风格。

### 3.3 需要平台能力档案，而不是页面特判

| 能力 | Mac 默认能力 | 手表默认能力 | 主题设计含义 |
|---|---|---|---|
| 指针 hover | 有 | 无 | 手表状态表达不能依赖 hover |
| 键盘与焦点 | 有 | 无 | Mac 必须保留系统焦点和快捷键 |
| 动态字体 | 应保留系统能力 | 固定生成字库 | 手表换字体需要重新生成资源 |
| 窗口尺寸 | 可变，有最小尺寸 | 固定 410×502 | 响应式规则不可直接共用 |
| 透明度与材质 | 可用，需服从系统设置 | 成本和功耗敏感 | 手表优先实色、少层、少重绘 |
| 阴影与复杂效果 | 可评估 | 默认克制 | 不得为了统一而给手表堆效果 |
| 动效 | 系统行为优先 | 短时、少量、可中断 | 循环动效只服务真实状态 |
| 色彩与功耗 | 常规显示约束 | AMOLED 纯黑有省电价值 | 手表背景不是任意换色项 |

主题可提供高阶表达意图，由平台能力档案决定如何实现和降级；页面不应写成大量
“如果当前主题且当前平台”的组合判断。

## 4. Mac / SwiftUI 的可借鉴方向

### 4.1 保留现有原生化基础

现有 `apps/mac/BeecordStudio/Common/DesignTokens.swift` 已集中管理空间、圆角、布局、颜色、
字体和动效，并通过 `cardStyle()`、空态、Toast 等共享组件形成初步一致性。后续应在该基础上演进，
不以建立另一套平行系统为目标。

应继续保留：

- SwiftUI 系统字体样式与等宽数字。
- 原生按钮、开关、菜单、焦点和禁用行为。
- 系统语义色及深浅色适配。
- 稳定 AX id 与 Accessibility Audit。
- 现有 SwiftPM、XCUITest 和 GitHub Actions 分层。

### 4.2 从“页面临时组合”转向“语义组件组合”

后续盘点重点不是数有多少个 HEX，而是识别：

- 同一语义是否在多个页面被不同方式组合。
- 组件状态规则是否只存在于某个页面。
- 页面是否通过 `.font`、`.foregroundStyle`、`.background` 反复拼出同类组件。
- 页面是否为了视觉修补引入额外条件分支和局部状态。

适合优先收敛的候选包括：侧栏导航项、状态徽标、工具行、库列表行、详情操作区、
确认对话框、权限面罩、进度反馈和内容卡。是否实施及先后顺序仍需独立评审。

### 4.3 主题注入应服务于组件，而不是制造全局分支

未来无论选择 Environment、共享样式类型或其他 SwiftUI 机制，都应遵守：

- 页面不读取主题名决定业务布局。
- 组件接收语义角色，不在内部散落硬编码风格。
- 主题变化不丢失 `@Observable` 业务状态、选中项和播放状态。
- 系统辅助功能环境优先于主题的装饰性选择。
- 样式入口保持少而明确，避免每个页面创建一套“主题管理器”。

本文不预选具体 Swift API，避免把方法论记录误当成实现定案。

### 4.4 辅助功能是主题约束，不是事后审计

Mac 主题评审应同时给出：

- 浅色与深色。
- 系统增强对比度下的可读性。
- 自定义透明效果在降低透明度时的回退。
- 自定义动画在减少动态效果时的回退。
- 键盘焦点、禁用、选中与 hover 的区别。
- VoiceOver 标签、状态值和朗读顺序不受视觉换肤影响。

现有 R10 对系统语义色采用平台基准；后续若引入固定自定义色，应单独验证实际合成背景的对比度，
不能把系统色豁免扩展到自定义色。

### 4.5 内容可视化需要独立语义

Beecord 的波形、播放进度、录音标记、同步状态和文件状态不是普通卡片文字。
主题应用时应定义其内容角色和状态关系，避免只改页面表面而留下旧图形配色。
同时保留波形的可访问标签与值，不能用视觉主题替换信息本身。

## 5. 手表 firmware / LVGL 的可借鉴方向

### 5.1 当前基础与真实缺口

固件已有以下基础：

- `firmware/main/ui/theme.h` 集中颜色、空间、圆角、字体和组件度量。
- `firmware/main/ui/theme.c` 统一屏幕、页面和文字基础处理。
- `firmware/tools/check_font_charset.py` 把文案与字库覆盖纳入宿主测试。
- `firmware/main/ui/ui_snapshot.c` 可在真实 LVGL 渲染后导出 BMP。

因此不需要从零建设“主题系统”。当前主要限制是：

- 主题主要是编译期宏集合，尚未形成可替换的完整风格描述。
- 页面仍负责大量组件样式组合，相同样板在多个页面重复。
- 通用文字入口仍要求调用方传入具体字体和颜色，语义角色约束较弱。
- 状态样式、组件变体和主题资源之间尚无系统化一致性测试。

这些是后续演进机会，不是要求立即重写。

### 5.2 从常量集中升级为语义样式与共享组件

手表端适合优先形成稳定的语义角色，例如：

- 屏幕底、页面底、卡片、次填充、浮层和遮罩。
- 标题、正文、辅助、弱信息、大时间、计时和数字。
- 主操作、次操作、危险操作、按住确认。
- 列表行、状态栏、状态小件、徽章、进度轨道与填充。
- 录音电平、标记刻度、REC 指示、同步状态。
- Toast、确认层、告警层、熄屏层和关机层。

页面使用这些角色和组件，不分别重复底色、圆角、字体、边线、按压态等属性组合。
组件仍有平台专用实现，不要求与 Mac 共享代码。

### 5.3 共享样式应减少重复，而不是增加运行路径分配

LVGL 方向应充分利用嵌入式环境特点：

- 相同样式集中定义、初始化并复用，避免每页重复拼装。
- 主题描述和静态资源优先只读、可放 Flash。
- 运行路径继续坚持无动态内存分配。
- 主题应用不得引入逐帧查表、运行时拼接样式或无界对象增长。
- 改主题时的对象刷新和样式失效必须集中处理，不能依赖每个页面自行记住刷新。

后续需要实测样式对象 RAM、字体与图像 Flash、首屏时间和重绘成本，再决定共享粒度。

### 5.4 先证明可替换，再决定是否提供运行时切换

手表首版更适合以下顺序：

1. 现有视觉作为唯一正式主题，先收清语义和组件边界。
2. 通过编译期配置或启动期选择完成一个内部试验主题，不开放用户入口。
3. 证明页面无主题特判、资源可完整生成、视觉与性能可验收。
4. 只有确有产品需求时，再评审运行时切换和持久化。

运行时切换不是主题架构正确的必要条件。对小资源设备，编译期或启动期方案可能长期更合适。

### 5.5 字体和图形资源属于主题交付物

手表换风格不能只替换颜色。字体角色变化会连带影响：

- 中文、数字、标点、占位符和特殊符号覆盖。
- 字体文件体积和 Flash 占用。
- 行高、基线、单行截断与组件最小高度。
- 大时间和秒显示的基线关系。
- 未对时、未知电量、长文件名等边界文案。

任何字体主题试验都必须重跑字库生成和字体门禁，并在真实设备快照中检查缺字、裁切和布局。
不能用宿主编译通过代替这些证据。

### 5.6 AMOLED、触控和实时业务是硬约束

- 纯黑页面背景目前兼具视觉与省电意义，不能因主题化自动变成普通可替换色。
- 卡片和浮层的亮度面积、循环动画与重绘频率应纳入功耗和性能评审。
- 安全区、圆角物理裁切和 48×48 最小触控目标不因密度主题而降低。
- 录音中熄屏不中断、错误提示唤醒、浮层优先级、按住停止时长均不属于主题表达。
- 切换视觉样式不得重建录音器、BLE 服务、文件索引或系统设置。

### 5.7 手表测试应复用现有宿主测试与快照体系

适合硬件无关测试的内容：

- 主题描述完整性：每个必需语义都有有效映射。
- 角色派生关系和非法值拒绝。
- 组件状态到语义样式的映射。
- 安全区、最小触控目标和密度下限。
- 主题资源清单与字库覆盖。
- 主题选择、持久化和回退的纯逻辑。

必须在设备或真实 LVGL 渲染中验证的内容：

- 实际字体度量、缺字和抗锯齿。
- 圆角物理裁切、对齐和视觉层级。
- 透明合成、颜色观感和 AMOLED 表现。
- 输入命中、浮层穿透、熄屏和唤醒。
- 重绘、内存、功耗与长时间录音中的稳定性。

`ui_snapshot.c` 是视觉验收基础，但快照仍须逐张读图，不能只检查 BMP 文件生成成功。

## 6. 跨端主题规格的未来形态

### 6.1 不急于生成代码，先稳定语义

早期最稳妥的方式是各平台用本机惯用代码表达同一套语义，并保留一份评审规格。
只有经过至少一次内部第二主题试验，证明语义集合稳定后，才值得评估共享结构化主题描述或代码生成。

过早做通用主题 schema 的风险：

- 把尚未理解的视觉需求固化成格式。
- 为平台差异增加大量可选字段和条件分支。
- 生成器、字体、图像和原生控件仍需平台专用逻辑，实际收益有限。
- 让简单换肤演变为高成本框架项目。

### 6.2 若未来建立共享描述，至少应有版本与能力约束

概念上应覆盖：

| 部分 | 内容 |
|---|---|
| 元信息 | 主题名、版本、继承关系、预期平台与能力要求 |
| 语义色 | 操作、文字、表面、状态、内容图形及必要状态变体 |
| 字体角色 | 角色用途、平台字体映射、回退和资源清单 |
| 空间与形状 | 密度预设、圆角、边线、组件尺寸约束 |
| 层次与材质 | 阴影、透明度、实色回退、浮层关系 |
| 图标与动效 | 图标族映射、时长、缓动、减少动效回退 |
| 组件映射 | 各组件状态引用哪些语义，不直接复制页面样式 |
| 验证规则 | 对比度、最小尺寸、字体覆盖、平台禁用能力 |
| 回退 | 缺资源、非法值、不支持能力时使用哪个完整主题 |

主题规格应描述意图和约束，不应成为任意脚本或页面布局 DSL。

### 6.3 共享测试向量比共享 UI 代码更有价值

Beecord 已在协议层使用共享 JSON 向量。未来主题语义稳定后，可借鉴这一思想：
用平台无关用例描述“语义角色 + 组件状态 + 平台能力”应得到的映射类别或约束结果，
由 Swift 与 C 各自消费。

适合共享的是契约和验收数据，不是 SwiftUI 与 LVGL 控件实现。

## 7. 测试与视觉验收方法

### 7.1 分层证据

| 层 | 主要断言 | 能发现 | 不能证明 |
|---|---|---|---|
| 语义/主题测试 | 必需角色、具体评审值、派生关系、非法配置 | 漏映射、误改色值、错误回退 | 页面是否美观、是否裁切 |
| 组件状态测试 | 默认、hover、pressed、selected、disabled、focus、loading、error | 状态遗漏、行为回归、旧色残留 | 整页信息层级 |
| 布局不变量 | 容器包含、最小尺寸、安全区、关键元素不重叠 | 操作出屏、物理裁切、密度越界 | 完整视觉效果 |
| 确定性场景渲染 | 同数据、同状态、同窗口或屏幕输出 | 绘制失败、状态场景缺失 | 人工视觉判断 |
| 截图读图 | 与原型及上一版本同场景比较 | 错位、层级、视觉不一致、异常空白 | 业务逻辑完整正确 |
| 真实环境 | 键盘、VoiceOver、系统显示开关、设备触控、功耗与长运行 | 平台和硬件特有问题 | 未覆盖场景 |

### 7.2 建议的确定性场景目录

场景目录应可复现，不依赖人工临时拼数据。后续实施时优先复用现有 Sim、合成 Ogg、
启动参数、LVGL 页面状态和快照能力。

| 页面/组件 | 首批应覆盖的状态 |
|---|---|
| Mac 设备页 | 空态、权限异常、已连接、下载中、失败、空文件列表 |
| Mac 录音库 | 空库、有文件、未选中、播放器、长文件名、删除确认、导出 |
| Mac 控制台 | 空态、帧日志、过滤、发送禁用、长内容 |
| Mac 设置 | 默认值、编辑、错误、凭据状态、开发者模式 |
| Mac 通用组件 | 侧栏、徽章、Toast、空态、进度、确认层、焦点与禁用 |
| 手表主页 | 未对时、正常时间、充电、低电、录音横幅、连接状态 |
| 手表录音页 | 录音、暂停、无卡、标记、按住停止中、写错误 |
| 手表通用层 | Toast、确认、告警、关机、熄屏、长文案和缺字边界 |

每个新主题不需要机械生成所有笛卡尔积。应先选能覆盖语义与组件的状态集合，
再为浅色/深色、标准/窄窗、正常/辅助显示和关键硬件状态补充定向组合。

### 7.3 “第二主题试验”是最有效的架构验证

仅有一个主题时，很难证明页面真的没有隐含依赖。后续可用一个不对外发布的试验主题验证：

- 不修改页面业务代码即可应用。
- 所有必需语义都被消费，没有旧主题残留。
- 组件状态和异常态与默认态一致演进。
- Mac 与手表仍保留各自平台习惯和约束。
- 发现缺失语义时回改共享规范，而不是给页面加特判。

试验主题只是测试手段，不等于需要新增用户可见风格。

### 7.4 若支持切换，必须单独测试状态保持

至少覆盖：

- Mac 下载中、播放中、库选中、设置编辑、窗口尺寸和滚动位置。
- 手表录音中、暂停中、标记、当前页面、浮层、熄屏状态和 BLE 连接。
- 连续切换、快速切换、资源缺失和回退。
- 切换后旧定时器、旧图标、旧字体和旧绘图颜色不残留。

### 7.5 不把全页像素 diff 作为唯一目标

自动像素比对容易受系统版本、字体、抗锯齿、色彩配置和渲染后端影响。更适合 Beecord 的组合是：

- 少量局部像素探针验证“某条线或光晕确实绘制”。
- 结构几何断言验证关键不变量。
- 自动输出同场景图片，人工逐张读图。
- 保留失败截图、AX 树或设备日志作为证据。

这与现有“自动化回归禁止截图比对，布局变更必须人工截图验收”的原则兼容；
未来若引入局部像素探针，只需明确它是例外，不放宽为整页脆弱比对。

## 8. 规范、原型与评审治理

### 8.1 文档职责

- `DESIGN_SYSTEM.md`：当前可实施的唯一视觉规范。
- `ux-design.md` / `ux-device.md`：当前交互与流程规范。
- 本文：未来架构方法论与候选方向，不直接授权编码。
- 后续独立实施方案：记录具体切片、改动范围、测试和回退，不重复堆叠本文原则。

### 8.2 新设计风格评审的最小材料

一种主题进入实现前，至少应提供：

1. 设计意图与不可变的产品语义。
2. 令牌角色和组件状态矩阵，而不只是几张默认页面效果图。
3. Mac 与手表各自的平台映射和降级规则。
4. 空态、错误、禁用、选中、焦点、长内容等关键状态。
5. 字库、图标、图像等资源变化及许可。
6. 对辅助功能、AMOLED 功耗、固件资源和性能的影响。
7. 同场景验收矩阵与回退方案。

### 8.3 避免“事实源”再次复制成多份

文档表格、代码常量、图版生成脚本和测试期望值应各自职责清楚：

- 规范说明为什么以及允许什么。
- 代码保存当前实现。
- 测试保存必须守住的契约，并提示同步评审。
- 图版尽量从可靠数据生成，或提供一致性检查。

如果生成脚本内部再手抄一份令牌，却没有与规范或代码对拍，只是增加第四份需要维护的数据，
不能称为真正的单一事实源。

## 9. 后续可选演进阶段（不是排期）

| 阶段 | 目的 | 主要产出 | 退出条件 |
|---|---|---|---|
| 0. 盘点与校准 | 不改动视觉，弄清现状 | 页面/组件/原始样式清单；文档与实现漂移清单 | 现有语义和例外可解释，校准项有评审结论 |
| 1. 当前主题语义化 | 用现有视觉证明抽象可行 | Mac 与手表各自语义入口；页面无视觉变化 | 全量行为回归通过，同场景截图无差异或差异已评审 |
| 2. 组件状态与场景门禁 | 把一致性问题前移 | 状态矩阵测试、少量几何断言、确定性场景目录 | 默认态和异常态均可复现，视觉证据完整 |
| 3. 内部第二主题试验 | 验证是否真正可换风格 | 一个非发布试验主题及平台映射 | 无页面主题特判，无旧色残留，资源与性能可接受 |
| 4. 产品能力决策 | 决定是否需要用户可见主题 | 独立产品提案、原型和切换/持久化方案 | 用户价值明确，完整验收和回退通过后才开放 |

阶段可以拆分、暂停或只做前三项。完成阶段 1/2 本身就有价值，不欠用户一个主题切换功能。

## 10. 优先级建议

### 优先借鉴

1. **语义与组件先行**：先统一决策层级，再谈主题切换。
2. **完整设计语言**：把字体、空间、形状、图标、动效和状态纳入同一风格评审。
3. **状态矩阵测试**：让默认态、异常态和辅助功能共同成为组件契约。
4. **确定性场景画廊**：同数据、同状态输出，逐张读图，不做全页像素唯一门禁。
5. **内部第二主题试验**：用实际换风格验证抽象，而不是凭类型名称判断成功。
6. **Mac 与手表共享语义、分别映射**：保留原生交互和硬件约束。

### 条件成熟后再考虑

- 共享主题 JSON 或代码生成。
- 用户可见主题切换和持久化。
- 第三方主题包或主题编辑能力。
- 跨端共享视觉测试向量。
- 自动色卡、组件图版和资源清单生成。

### 暂不值得投入

- 通用跨平台 UI 框架。
- 为所有原生控件自绘一套外观。
- 一次性迁移全部页面的大爆炸改造。
- 大规模逐像素黄金图库。
- 仅为形式一致而进行的全量类型改名。

## 11. 典型反模式

- 页面读取主题名，然后选择本地颜色或字号。
- 把所有页面尺寸都放进全局令牌，导致业务布局无法演进。
- 只有颜色角色，没有组件状态角色。
- 为换肤重写系统按钮，结果丢失焦点、键盘或朗读。
- 用大量透明色和阴影制造层次，却不验证最终合成背景与辅助显示回退。
- Mac 与手表使用同一张数值表，忽视动态字体、触控、AMOLED 和字库限制。
- 主题切换通过重建整个 App 或 UI 任务实现，导致业务状态丢失。
- 固件每页各建一套相同样式对象，增加 RAM 和漂移风险。
- 只检查图片生成数量，不逐张读图。
- 文档、生成器、代码和图版各复制一份数据但互不对拍。
- 为支持假设中的未来主题，提前引入复杂依赖和配置系统。

## 12. 后续实施时可量化的指标

这些指标用于判断演进是否有效，不要求当前立即全部采集：

- 页面层直接引用原始色值、字号和组件状态组合的数量。
- 同类组件不同实现的份数。
- 有完整状态矩阵和测试的共享组件比例。
- 可从固定场景一键复现的关键页面状态比例。
- 内部第二主题试验中需要修改页面业务文件的数量。
- 主题应用后残留旧资源的失败用例数。
- Mac 辅助功能审计新增未豁免问题数。
- 手表主题样式 RAM、字库与图像 Flash、首屏时间和重绘成本。
- 手表安全区、触控目标和字库覆盖违规数。
- 主题切换过程中的录音、下载、播放和连接状态保持率。

## 13. 当前已登记的规范校准项

以下是本次对照时发现的事实源漂移，**仅登记，不在本文拍板修复方向**：

1. Mac `state.recording` 在 `DESIGN_SYSTEM.md` 写为 `#E5484D`，
   `DesignTokens.swift` 当前使用系统红色。需评审究竟保留固定录音色还是采用系统动态色。
2. Mac 工具行规格和代码注释描述为 12px，`DesignTokens.FontToken.toolRow`
   当前映射到 `.caption`，与文档的 caption 参考值存在差异。需评审规格、注释和实现谁应调整。

这些问题适合在未来阶段 0 统一校准，然后再写契约测试；不应在架构改造中偷偷改变视觉。

## 14. 后续规划时必须单独决策的问题

1. 哪些产品语义跨主题绝对不变，哪些允许风格化表达。
2. 品牌色、系统强调色和用户系统设置之间的优先级。
3. 首版只需要“可替换架构”，还是确有用户主题切换需求。
4. Mac 自定义固定色的对比度政策如何与现有 R10 衔接。
5. 手表纯黑背景与 AMOLED 功耗是否是长期硬约束。
6. 手表采用编译期、启动期还是运行时主题应用。
7. 字体和图标资源如何版本化、生成、验收和回退。
8. 是否确实需要共享主题描述；何时才有足够稳定语义支持它。
9. 哪些少量布局不变量值得自动断言，哪些仍交给读图。
10. 主题切换是否允许改变密度和字体尺度，以及如何保护内容地板。
